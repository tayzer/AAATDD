# Open questions and serious risks

Updated: 2026-11-05. See the [decision sequence](design-status.md) and [architecture reconciliation](architecture/2026-10-26-design-reconciliation.md). Agreed directions do not settle their unapproved mechanisms.

## Resolved

- **Q1 — approval boundaries:** [ADR 0001](decisions/0001-separate-intent-and-baseline-approval.md) accepts two checkpoints, with a combined review allowed for a clear small change. Remaining lifecycle details are not accepted by this decision.
- **Q15 — clarification boundary:** [ADR 0002](decisions/0002-clarify-acceptance-changing-uncertainty.md) accepts human clarification for acceptance-changing uncertainty, routine choices within approved constraints, explicit deferral of affected scope, and escalation when the boundary is unclear.
- **Q16 — format support only:** [ADR 0003](decisions/0003-support-change-appropriate-specification-artifacts.md) accepts conditional support for DSL scenarios and work without a mandatory behavioural DSL scenario. The remaining contents and readiness questions stay open below.
- **Business-specification authority:** [ADR 0004](decisions/0004-gherkin-business-specification-authority.md) makes Gherkin authoritative; OpenAPI, Pact and other tests are complementary. This explicitly revises the earlier charter framing, with no prior ADR superseded.
- **Q17 — general direction only:** the 2026-10-26 update agrees classification by type and risk, an evaluable objective for every change, and prevention of verification downgrades through labels. Detailed sufficiency and enforcement remain open below.
- **Q20 — assurance staging:** [ADR 0005](decisions/0005-validate-l1-before-protected-l2.md) accepts an explicitly L1/advisory first slice with a separately running SUT, followed by protected L2 validation before independent-assurance claims. Slice implementation and detailed acceptance criteria remain unapproved.
- **Q22 — initial business scope:** [ADR 0006](decisions/0006-bound-the-initial-orders-example.md) accepts the bounded synchronous, atomic example and its two [Gherkin scenarios](requirements/order-stock-validation.feature) at the intent checkpoint. The executable baseline, observation exceptions and implementation are not approved.
- **Q23 — observation split:** [ADR 0007](decisions/0007-use-public-outcomes-with-scoped-order-observation.md) accepts public HTTP for the result/stock, plus read-only database observation within the isolated test store for persisted orders when no adequate public query exists. A concrete provider and exception are not yet approved.
- **Q24 — sample storage:** [ADR 0008](decisions/0008-use-disposable-sqlite-per-scenario.md) accepts one disposable named SQLite file per scenario with fixture-owned seed/cleanup and a distinct read-only observer connection. It is sample-specific and does not approve versions, schema, a concrete exception or implementation.
- **Q7 — core outcome semantics only:** [ADR 0009](decisions/0009-distinguish-requirement-failure-from-invalid-verification.md) accepts `PASS`, `FAIL` and `INDETERMINATE`, with only `PASS` permitting completion. It distinguishes trustworthy requirement failure from invalid/missing verification, including mixed evidence and globally invalid oracles. Remaining policy details stay open below.
- **Q7 — initial retry policy:** [ADR 0010](decisions/0010-preserve-failures-across-explicit-reruns.md) accepts no automatic scenario retries in the first experiment, retained explicit reruns and authorised resolution of earlier trustworthy failures. It does not settle every project's retry or waiver policy.
- **Q6 — identity model:** [ADR 0011](decisions/0011-separate-logical-baseline-and-run-identities.md) accepts stable explicit logical IDs, content-based baseline revision, separate implementation/environment identity and individual run IDs. Concrete encodings, namespaces and generated-case rules remain open below.
- **Q4 — initial boundary:** [ADR 0012](decisions/0012-bound-the-initial-oracle-to-harness-inputs.md) accepts the dedicated acceptance harness plus identified external execution inputs, with the SUT tracked separately. Concrete inventory, validation and amendment rules remain open below.
- **Q8 — conceptual lifecycle:** [ADR 0013](decisions/0013-separate-baseline-authority-from-verification.md) accepts `DRAFT`, `APPROVED` and `SUPERSEDED`, scoped authority before passing verification, new drafts for amendments and explicit supersession retaining history and unaffected obligations. Detailed mechanics and broader starting-evidence policy remain open below.
- **Q5 — first-harness validation policy:** [ADR 0014](decisions/0014-require-targeted-first-harness-validation-controls.md) requires a positive control and targeted negative controls for behavioural faults, unapproved oracle edits and failed setup/observation before accepting first-harness validation evidence. Concrete variants, general adequacy and later revalidation policy remain open below.
- **Q23 — initial HTTP mapping:** [ADR 0015](decisions/0015-agree-initial-sample-http-mapping.md) accepts `POST /orders`, explicit `201` acceptance and `409` insufficient-stock response bodies, plus a `200` stock query through `GET /products/{sku}/stock`, with the agreed fields and matching identities. Correlation adds no idempotency promise. Detailed wire validation and consistency mechanics remain open below.
- **Q19 — initial sample completion/read consistency:** [ADR 0016](decisions/0016-observe-completed-sample-operations.md) accepts completed atomic acceptance or definitive rejection before the response, followed by committed-state observations using a fresh observer read transaction. No polling hides incomplete work; an empty query establishes absence only at its declared read point. Concrete settings and broader temporal semantics remain open below.
- **Q18 — initial fixture readiness:** [ADR 0017](decisions/0017-validate-fixture-readiness-before-submission.md) accepts database/public-stock validation against the feature before submission, distinct setup/outcome checks, blocked submission for unestablished preconditions, a wrong-seed control and preservation of separately trustworthy failures. Concrete validation, observer queries and reusable APIs remain open below.
- **Q18 — initial outcome-observer scope:** [ADR 0018](decisions/0018-inspect-all-scenario-owned-orders.md) accepts inspecting all scenario-owned orders, expected counts and customer/product/quantity/request identities, plus accepted-order correspondence with response `orderId`. Concrete queries, provider identity and the observer exception remain open.
- **Q18 — initial teardown:** [ADR 0019](decisions/0019-require-confirmed-scenario-teardown.md) accepts cleanup attempts after execution/setup failure, established ownership limits, release before owned-file deletion, confirmed cleanup for `PASS` and separate preservation of behavioural results/diagnostics. Concrete mechanics and retention remain open.
- **Q18 — initial component model:** [ADR 0020](decisions/0020-use-scenario-scoped-harness-components.md) accepts ordinary scenario-scoped fixture, HTTP-helper, observer and binding/assertion responsibilities, separating measurement from acceptance and deferring provider registries/published extension APIs until demonstrated reuse. Concrete APIs and reusable contracts remain open.
- **Q12 — initial evidence composition:** [ADR 0021](decisions/0021-retain-native-messages-with-aaatdd-envelope.md) accepts retained native Cucumber Messages plus an AAATDD approval/provenance envelope, with CTRF optional and derived. Unsupported/incomplete evidence blocks `PASS`; native success alone cannot establish approved coverage. Concrete schemas, versions and producer validation remain open.
- **Q14 — initial sample stack:** [ADR 0022](decisions/0022-select-dotnet-reqnroll-for-first-experiment.md) accepts C#/.NET with a Reqnroll acceptance harness and a separately running ASP.NET Core sample API. ADR 0023 subsequently selects the test framework/platform; exact versions and AAATDD framework/verifier language remain open.
- **Q14 — test framework and platform:** [ADR 0023](decisions/0023-use-mstest-with-microsoft-testing-platform.md) records the user's explicit choice of MSTest and MTP. NUnit was not selected. Exact versions and platform configuration remain open; ADRs 0024–0025 settle scheduling and SDK arrangement.
- **Q14 — initial scenario scheduling:** [ADR 0024](decisions/0024-run-initial-scenarios-serially.md) accepts disabled scenario parallelism with independent setup/ownership and no order dependency. Exact configuration and future parallel-execution validation remain open.
- **Q14 — harness SDK arrangement:** [ADR 0025](decisions/0025-use-mstest-sdk-for-acceptance-harness.md) accepts `MSTest.Sdk` with `Reqnroll.MSTest`, keeping the sample API separate. Exact target/version configuration and generated-test/discovery/native-message integration remain pending review.
- **Q14 — initial target framework:** [ADR 0026](decisions/0026-target-net10-for-first-sample.md) accepts .NET 10 LTS (`net10.0`) with a stable .NET 10 SDK for both sample projects. Exact patches/packages and integration validation remain pending review; this does not select the framework/verifier target.
- **Q24 — sample provider approach:** [ADR 0027](decisions/0027-use-microsoft-data-sqlite-with-direct-sql.md) accepts Microsoft.Data.Sqlite with direct parameterised SQL for SUT persistence, fixture setup and distinct read-only observation. ADR 0028 settles the minimal schema; exact versions/native dependencies, settings and the observer exception remain open.
- **Q24 — minimal schema:** [ADR 0028](decisions/0028-use-minimal-inventory-and-orders-schema.md) accepts the `inventory`/`orders` table/column structure, text identities, integer quantities, non-null fields, SKU/order primary keys and non-unique request correlation. Actual SQL and additional constraints remain pending review.
- **Q24 — initial connection profile:** [ADR 0029](decisions/0029-use-explicit-sqlite-connection-roles.md) accepts fixture `ReadWriteCreate`, SUT `ReadWrite`, observer `ReadOnly` and disabled pooling throughout. Concrete configuration, versions and the observer exception remain open.
- **Q4 — initial pinning/restore controls:** [ADR 0030](decisions/0030-pin-sdks-and-use-locked-restore.md) accepts exact SDK/project-SDK pins, reviewed NuGet lock files, locked restore without automatic regeneration/force-evaluation and explicit update review. Actual runtime and managed/native identities remain separately required. Exact versions/configuration and full inventory remain open.
- **Q14 — direct validation targets:** [ADR 0031](decisions/0031-select-direct-version-validation-targets.md) selects SDK `10.0.403`, MSTest SDK `4.5.2`, aligned Reqnroll `3.3.4` and Microsoft.Data.Sqlite `10.0.14` for compatibility validation. Full transitive/native resolution and executable-baseline approval remain pending. This grants no implementation/execution authority.

## Unresolved

**Implementation update:** the autonomous release goal now delegates routine engineering choices under [ADR 0041](decisions/0041-authorise-autonomous-release-implementation.md). The CLI, baseline store, real runner/evaluator, Orders example and a packaged second-project onboarding control are implemented. TADA source uses MIT and the local development package ID is `Tada.Cli`; final public name availability and publication are not established. The entries below retain the design-stage questions; consult the [release checklist](release-readiness.md) for live gaps rather than treating every old mechanism question as a pending user approval.

[ADR 0040](decisions/0040-define-alpha-scope-and-expected-cases.md) accepts the alpha scope/case shape, explicit tag-based logical IDs with grammar `[A-Z][A-Z0-9_]*`, ordinal ID/case ordering, source traceability and pre-filter coverage accounting. Only ordinary scenarios are supported; Scenario Outlines are explicitly rejected pending future row-identity design. Other inventory field schemas, tag-role classification and native evidence mapping remain open.

[ADR 0039](decisions/0039-define-alpha-inventory-structure-and-ordering.md) accepts seven top-level inventory fields, keyed-set versus ordered-sequence rules, relative repository-file paths, pinned policy/exception references and approval blocking for unresolved required inputs or unapproved exceptions. Detailed field schemas, exact unique keys and path-resolution mechanics remain open.

[ADRs 0037](decisions/0037-hash-oracle-input-files-as-exact-bytes.md) and [0038](decisions/0038-use-sha256-and-rfc8785-for-baseline-inventories.md) accept exact-byte input-file hashing, SHA-256 digests represented as `sha256:` plus 64 lowercase hexadecimal characters, and RFC 8785 canonical JSON for generated baseline inventories. No automatic approval carries forward after formatting changes. ADR 0039 supplies inventory structure and ordering policy; detailed field schemas and other concrete identity rules remain open.

[ADR 0036](decisions/0036-bind-approval-to-reviewed-baseline.md) accepts the alpha review-to-approval binding: immutable baseline revisions, separate review and approval records, unchanged reviewed inputs, explicit revision selection and explicit replacement scope. Q8's concrete identifiers, digests, schemas, storage and flags remain open; review records do not authenticate human approval in L1.

[ADR 0034](decisions/0034-rename-tool-to-tada.md) renames the tool to TADA (Test-Assured Development Assistance), with command `tada`. [ADR 0035](decisions/0035-adopt-five-operation-alpha-cli.md) accepts the five-operation alpha CLI and shared rules. Package identity, exact flags, configuration, numeric exit codes and approval-record formats remain open; accepted historical records retain AAATDD wording.

The first release boundary is accepted in [ADR 0032](decisions/0032-bound-the-first-publishable-alpha.md): a local L1/advisory `0.1.0-alpha`, supporting one developer and Git repository with Reqnroll/MSTest/MTP on Windows x64/.NET 10. [ADR 0033](decisions/0033-use-dotnet-local-tool-for-alpha-verifier.md) selects C#/.NET 10 for the verifier and NuGet distribution as a repository-local .NET tool with a pinned manifest version. These partially resolve Q14; package identity, distribution controls, detailed command contracts, dependencies, licence and detailed contracts remain open. Deferred capabilities below remain future questions rather than mandatory alpha scope.
